# 航点净空与「原地待命」的停车位

> 现场原话：「任务结束选原地待命时，常出现终点附近有障碍物，路径无法结束。」
> 这份文档记录 2026-11 的定位结论、判据、代码位置，以及**厂商侧还缺什么**。

## 1. 结论：不是狗不听话，也不是指令发错

- `endTaskMode = none`（原地待命）时，**最后一个航点就是停车位姿**——本体
  `5000 kind=4` 的 `params.end_task = 0` 就是这个意思（`business/client/src/zhpro/route.rs::patrol_end_task`）。
- 本体规划器要求目标点在 free 栅格上、离障碍留出膨胀余量。目标被判成占据时它
  **正确地拒绝出轨迹**，报 `13377 无有效绕障轨迹，搜索失败，等待中`，常伴
  `13446 全局规划失败，目标被障碍物占据` + `13440 导航指令非法`
  （判读表见 `deploy/robodog-body.md` §10.8）。
- 于是 5009 停在「前往 P{n}」，既不终态也不报错；平台一直显示「执行中」，
  计划灯、调度窗口、设备台账全跟着挂住。

责任划分：**本体拒绝是正确行为**；我们这边有三处缺口——终点净空从来不校验、
UI 没把「最后一点是停车位」说清楚、卡住之后没有兜底。前两处本项目已修，见下。

## 2. 判据（现场实测，不是拍脑袋）

| 阈值 | 含义 | 出处 |
| --- | --- | --- |
| **≥ 0.5 m** | 停车位 / 航点的建议净空 | 2026-11-14 复盘：0.50 m 的点本体可达，再近开始吃 `13377`（`deploy/robodog-body.md` §10.8） |
| **< 0.15 m** | 点基本落在障碍 / 膨胀层里，**任何**结束动作都规划不过去 | 同一份复盘里 `13446` 的判据 |

`clearance` 是**到最近占据格的欧氏距离**。地图栅格里 `0`=占据、`128`=未知、`254/255`=free：
**只认占据格**，未知格不算障碍——现场地图动辄 8 成是 unknown，把它算障碍会让
每个点都报净空不足，校验就没人看了。

## 3. 服务端：算净空 + 拦在发布/校验

`business/server/src/handlers/maps/clearance.rs`

- 从 `map_versions.file_path` 指向的地图包（zip）里读 `map_edit/map.pgm` / `map.pgm`，
  用 **Felzenszwalb 精确 EDT** 算平方距离场（两趟一维变换），再取 sqrt。
  不用多源 BFS 的曼哈顿距离：斜向会高估 41%，正好是「消息说 0.7 m、本体还是进不去」的误判方向。
- 坐标口径与 `coords::MapFrame` 完全一致（原点取 `map.yaml`、分辨率、图像 y 向下）。
- 栅格尺寸与 `map_versions.map_width/height` 差超过 1 格 → **返回 `None`**（图与几何
  不是同一份，宁可不给净空也不能给错的）；一个占据格都没有 → 同样 `None`。
- 结果按 `map_id|file_path` 缓存（`OnceLock<Mutex<HashMap<..>>>`），地图包换了 key 就变。

接线位置：

| 接口 | 行为 |
| --- | --- |
| `POST /routes/{id}/validate` | 新增两项：**终点停靠净空**（最后一个点）与**航点净空**（全路线最小值）。解不出栅格时两项都不出现（不让「没有地图包」变成校验失败） |
| `POST /routes/{id}/publish` | 任一点净空 `< 0.15 m` → **拒绝发布**（点落在障碍上，谁都跑不了）；终点 `< 0.5 m` → 允许发布但在 `task_events` 留痕（同一条路线也可能配「返回起点」） |
| 任务下发（`handlers/tasks.rs::warn_parking_clearance`） | 结束动作**真的会停在最后一点**（显式「原地待命」，或「跟随路线」+ 往返/单向）且终点 `< 0.5 m` → 在任务时间线写一行提醒（不改状态、不拦下发）。闭环 + 跟随路线仍会返航，不提醒 |

## 4. 客户端：卡在最后一点不再干等

`business/client/src/zhpro/route.rs::final_point_stall_reason`

判定条件（三个同时满足）：

1. 「只剩最后一个航点没到」：`5009 detail.last_arrived_point.index == total - 2`（0 基）；
2. 这个状态持续 `FINAL_POINT_STALL_WINDOW` = **150 s**；
3. 这段时间里 `4021` 故障码中**规划类**（`13377` / `13446` / `13440`）出现
   ≥ `FINAL_POINT_STALL_FAULTS` = **3** 次。

命中就带一句人能看懂的原因结束任务（→ 平台「异常」+ 企业微信推送），而不是等
`180 s/点` 的总超时（5 个点要 15 分钟）。文案里点名 `code=`、「原地待命」的语义、
以及「把终点往空旷处挪 0.5 m / 清走障碍物」的改法。

为什么只认「只剩最后一个点」：中途点卡住是另一个问题（多数是起点净空或定位降级），
「返回起点 / 返回充电点」时最后一个点已经到过，`last_arrived` 变成 `total-1`，
天然不会误判。定位类（`13120`/`13136`/`13381`）与传感器类（`12672`/`13504`）
故障码**故意不算**：那要修的是定位和传感器，报成「终点被占」会把现场带偏。

故障码从哪来：`4021`（`T_FAULT_CODE`）在 `pump.rs` 里除了上报平台，还
`client.note_fault(code)` 记进客户端本地日志（`ZhProClient::recent_fault_codes`，
10 分钟 / 256 条封顶）。

## 5. 厂商侧还缺什么（2026-11 核实）

`business/docs/zhihang-pro-api-v1.0.3.txt` 里：

- `goal_tolerance`（到点容差）**只有 `5000 kind=2` 导航任务有**（§2.5.1.4 字段表）；
- `5000 kind=4` 巡检任务**没有字段表**（文档标注「暂不对外开放」，我们是从官方 App
  抓的报文反推的，见 `route.rs::patrol_task_payload`）；
- `4024 add_nav_path` 的路径点只有 `properties:{type, tasks}`（§2.2.3.7），
  **没有半径 / 容差字段**。

所以「原地待命」目前只能是**严丝合缝地到点**，没有办法「差 0.3 m 就收尾」。
要根治得向厂商要：巡检（kind=4）的 `goal_tolerance`，或路径点的停靠容差
（等同「到达半径内即视为到点」）。拿到之前，只能靠上面的校验 + 兜底。

## 6. 还没做（下一步）

真正的解耦是把**停车位从最后一个巡检点里拆出来**：任务级可选「收尾停靠点」，
下发时作为路线末尾多追加一个无动作的途径点，`end_task = 0` 就停在那里。
现在没做的原因：会多一个点位下标，`task_progress` 的「N/N」、航点 AI 窗口
（按 `waypointIndex` 索引动作）都要跟着对齐，属于跨平台/客户端/板端的改动，
要先设计再动（见 `AGENTS.md` 里关于 `waypointIndex` 的那段事故记录）。

## 7. 回归

```bash
cd business/server && cargo test --lib handlers::maps::clearance handlers::routes
cd business/server && cargo test --test route_clearance
cd business/client && cargo test --bins final_point fault_log
```

- `tests/route_clearance.rs`（黑盒）：现造一张「一堵墙」的 PGM 地图包 →
  终点离墙 0.1 m 的路线校验「终点停靠净空」不通过、发布被 400 拒绝且原因写明「障碍」；
  离墙 0.5 m 的路线两项都通过并发布成功；**地图包缺失时净空项直接不出现、也不拦发布**
  （否则没地图包的园区永远发布不了）；

- `handlers::maps::clearance::tests::*`：距离场（障碍格为 0、邻格一格距、斜向走欧氏）、
  未知格不算障碍、图与几何不一致直接放弃、图外点不给净空、点序号从 1 开始；
- `handlers::routes::tests::*`：终点净空不足 → 「终点停靠净空」不通过且文案带 `13377`、
  中间点贴障碍也要报、空点列表不产生校验项；
- `zhpro::route::tests::final_point_stall_*`：只剩最后一点 + 3 次规划故障才判；
  中途点 / 故障次数不够 / 窗口没到 / 只有定位类故障 / 单点航线 / 返程任务都不误判；
- `zhpro::client::tests::fault_log_keeps_recent_codes_only`：同一故障重推各自计数。
