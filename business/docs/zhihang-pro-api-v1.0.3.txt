本体 WebSocket 通过同一端口承载两条逻辑连接： control 用于会话建立、控制请求和小数据消
息； bulkdata 用于大负载数据传输。上述两条连接须归属于同一逻辑客户端 client_id 。​
1.1.1 访问地址
 💡 M1 / L2 的智航地址为 192.168.168.100，对应控制接口连接地址为
      ws://192.168.168.100:10010/control               。​

连接​                  地址​                               用途​
 control   ​         ws://host:10010/control   ​       握手、心跳、控制请求和响应​
 bulkdata      ​     ws://host:10010/bulkdata      ​   大负载数据传输​

两条连接共用端口 10010 ，通过 URL path 区分连接角色；host 须替换为实际部署的机器人或网关
IP 地址。​
1.1.2 逻辑关系
  代码块​
  1    Logical Client (client_id = N)​
  2    ├── control         -> /control​
  3   └── bulkdata   -> /bulkdata​



client_id由网关在 1201 握手应答中分配。 control 与 bulkdata 不可作为两个独立客户
端使用， bulkdata 须绑定至与 control 相同的 session_id 。​
 💡 Bulkdata 通道主要为部分高频推送数据所使用，主要为1401，1403，1405，1407推送数据​
1.1.3 建链约束
1. 必须先建立 control ，并取得 1201 返回的 session_id 与 bulkdata_bind_token 。​
2. 建立 bulkdata 后，首个数据帧必须发送 1202 绑定请求。​
3. 1202.data.session_id 和 1202.data.token 必须分别使用 1201 返回的会话 ID 和绑
   定令牌。​
4. 只有收到 1203 后， bulkdata 才视为绑定成功，可以继续传输业务数据。​
1.1.4 标准建链时序
1. 客户端连接 ws://host:10010/control 。​
2. 网关主动返回 1201 kHandShakeAck ，客户端保存 client_id 、 session_id 和
    bulkdata_bind_token 。​

3. 如需重新获取会话信息，客户端可在 control 上发送 1200 kHandShake ，网关再次返回
    1201 。​

4. 客户端连接 ws://host:10010/bulkdata 。​
5. 连接建立后的第一条消息发送 1202 kBindBulkDataChannel 。​
6. 网关返回 1203 kBindBulkDataChannelAck ，确认绑定成功。​
7. 绑定成功后，客户端再发送或接收需要走 bulkdata 的业务消息。​
1.1.5 建链失败处理
场景​                        处理​
 control连接失败​              不得建立或继续使用 bulkdata ，应先重建 control 。​
bulkdata 首帧不是 1202 ​       网关拒绝绑定，客户端关闭该连接并重新建立 bulkdata 。​
会话 ID 或令牌校验失败​             丢弃当前 bulkdata 会话，重新获取 1201 后再绑定。​
未收到 1203 ​                 不得发送业务数据；按超时策略重试绑定。​
1201   成功后，客户端须保存 session_id 、 bulkdata_bind_token 和 client_id ；
bulkdata 通道建立后须立即发送 1202 。 1207 的 data.modules[].available 用于判断
SDK、本体桥接模块是否可用；当连续约 3 秒未收到 SDK 1525 心跳时，gateway 将对应模块置为
不可用。​

2.1 API 使用约定​
传输方式。所有请求、响应、通知和推送均通过 WebSocket 文本消息传输，消息统一由 head 和
data 两部分组成。​

请求与响应。请求消息的 src=1 ，算法响应的 src=2 ；使用 msg_id 关联同一请求的响应。客
户端应先校验 head.type 和 msg_id ，再解析 data 。​
通知与推送。通知、状态和实时数据由算法主动发送，不与请求建立一一对应关系；客户端按
head.type 分发，并分别维护事件、状态和实时数据。​

错误处理。响应优先判断 data.code ： 0 表示受理或处理成功，非 0 表示失败；再结合
data.msg 和业务字段展示结果。控制类响应仅表示请求受理，任务最终结果以状态推送或结果通
知为准。​
本章按 API 参考格式组织，覆盖公共消息头、事件通知、地图与路径、定位、任务控制、状态上报和
巡检记录。每个接口均以 type 为索引，说明方向、请求或推送条件、data 结构和客户端处理方式。​

2.2.1.2 回充 / 出桩底层结果通知 5019 ​
 5019 表示底层充电 / 出桩处理结果已确定，不表示请求是否受理。请求是否受理以 5001 或​
 5015 为准，导航至充电点等过程状态以 5009 为准。底层结果为取消 / 主动停止时不推送
 5019 。​

 data.status 的取值规则按 task_type 区分（回充与出桩分别适用独立的状态判定逻辑）：​


task_type​             成功​1              2 失败​           3 满电保持​

 recharge /         确认进入充电状态 —— 两 底层 arc 报 FAILURE / 底层 phase ==
 return_to_charge ​ 节电池任一节               STOPPED ，或状态流中 recharge_completed ​
                     power_supply_status 断触发保活超时​
                    == 1 （CHARGING）并持
                    续 3 秒​
 undock ​           底层 arc 报 SUCCESS ​   同上​            不适用​

推送时机独立于任务终结状态。 回充任务在充上电之后不会立即结束（大状态持续 1 运行中，​
子状态转 43 充电中 / 45 满电保持），所以：​
• status = 1 在确认进入充电状态时推送，此时任务仍在运行；​
• status = 3 在底层报 recharge_completed 时推送一次（不重复推）；​
• status = 2 在任务失败终结时推送。​
同一回充任务可能依次收到 1 和 3 两帧。​

字段​                    类型​                 说明​

                                           tasks ）​
 tasks   ​             number[]​        作业动作类型序列，按数组顺序依次执行。取值见下表；空数组 /

 tasks       取    动作​               说明​
值​
 0​               等待​               在该点停留一段固定时长（当前实现 2 秒）​
 1​               拍照​               调用上装拍照（ /capture_image ），异步 + 超时；失败只记录，不中断巡
                                    检​

约束（算法侧按此校验，违反即忽略并告警，但不会让整条路径加载失败）：​
• tasks 是动作类型，不是"作业项 ID"——当前取值闭集为 {0, 1} ，其它数字一律视为非法并
  丢弃；​
• type=0 的途径点不执行任何动作：即便写了 tasks 也会被忽略（要执行请把该点标为
  type=1 ）；​

• 同一动作可重复出现（如 [0, 1, 0] = 等待→拍照→等待）。​
 与 5000 巡检任务内联点位（§4.1.7 的 goals[].actions[].type ）取值口径一致，两处都
 是 0 等待 / 1 拍照。​

2.5.5 自主返航回充 5014/5015 ​
用于指示机器人导航至当前地图已设置的回充点位（协议 4018 ），并自主对桩充电。与上文各条不
同，本指令不依附于任何任务、不携带 task_id ，可在任意时刻下发；服务端将新建一个『返回充
电点』任务，并在响应中返回其 task_id 。​
 与 5000 kind=3 回充任务的区别： kind=3 是无图一键对桩（在充电桩附近直接对桩，不导
 航、不需要地图）； 5014 是先导航到预设回充点、再对桩，因此要求已载入地图且该地图设过回
 充点。​
 与巡检 end_task=2 的区别： end_task=2 是创建巡检任务时约定"跑完最后一个航点再返
 充"； 5014 是任意时刻临时触发。二者复用同一套"导航到回充点 → 对桩"逻辑。​
当前有任务在跑时的处理：​
当前状态​                              处理​
空闲​                                直接执行​
巡检中​                               先取消巡检，等其停稳后自动执行； task_id 在响应里立即返回，期
                                   间可用 5002 取消本次返航​
回充中 / 已在返回充电点途中​                   幂等：直接返回成功， data.task_id 为既有任务的 id，不新建、不
                                   打断​
建图 / 导航 / 定位中​                     拒绝（ 0x3649 资源冲突）。不擅自打断其它作业——建图中途停止会
                                   丢失未保存的地图​

2.6.10 用户端(APP) 接入规则​
1. 每收到一帧 5009 ，整体替换本地机器人任务快照，不要把多帧按任务自行拼接。​
2. 同一 boot_id 内按 snapshot_seq 丢弃重复或更旧快照； boot_id 变化时清空旧任务和
   事件游标。​
3. 使用 current_task.lifecycle 判断运行 / 暂停 / 终态，使用 stage 判断业务阶段；
   robot.task_state 只表示任务占用状态，不等同于底盘运动、充电或定位状态。​
4. pending_task 表示已受理但尚未驱动底盘，仍可使用其 task_id 调用 5002 取消。​
5. 即时终态可能出现在 current_task ；回收后仍会短暂存在于
   recent_terminal_tasks 。用户端(APP) 两处都应识别，并按 task_id + lifecycle
   幂等处理。​
6. 5017 和 5019 仍是各自业务结果通知，不能由 5009.last_event 替代。​
网关收到客户端 1501 上线通知后，ALG 会向该客户端定向推送一帧完整 5009 快照；客户端刷新
或重连后不需要等待下一次周期心跳。​

字段​                      类型​         说明​
head.type​               number​     消息类型，固定为 5021 ，表示删除巡检记录响

data.code​               number​     结果码。 0 = 全部达成； 14003 ( 0x36B3 ) = 部

                                     只记日志，不下发）​
data.remaining_total​    number​     删除后剩余的巡检记录总条数​

语义约定​
• 幂等性：请求中指定的任务 ID 即使已不存在，也计入 deleted 。服务端以“记录已不存在”作
  为成功结果，无需区分记录已被本次请求删除还是此前已被其他客户端删除或自动清理。​
• 部分成功：单条记录因权限或 I/O 错误删除失败时，服务端继续处理其余记录，并将失败项写入
  failed 。处理完成后返回 code = 14003 （ 0x36B3 ），同时返回完整的 deleted 、
  failed 和 remaining_total 。客户端应依据明细更新本地数据和界面。​

• 部分成功的结果码：部分记录删除失败时不得返回 code = 0 。 code = 0 仅表示请求涉及的
  全部记录均已达到“不存在”状态；非零结果码用于确保客户端不会将仍存在的记录误判为删除成
  功。​
• 索引一致性：无论本次处理是否存在失败项，服务端均重建摘要索引 index.json 。索引内容应
  与本次删除结果保持一致，不保留已删除记录。​
• 整批原子拒绝：当 task_id 缺失、类型非法、为空数组、元素非字符串，或数组超过 20 条、
  单个 ID 超过 64 个字符时；以及任一 ID 等于 . 、 .. 或保留名 index ，包含路径分隔符
  （ / 、 \ ）或 NUL 字节（ \0 ）时，服务端返回 code = 0x364A ，本批请求不删除任何记
  录。仅当 ID 完整等于上述保留值时才拒绝；例如 a.b 和 index.json 均为合法 ID。​
• 列表刷新：客户端可使用 remaining_total 更新列表总数，无需再次请求 5010 。当
  failed 非空时，建议重新请求 5010 ，以校准列表明细。​


3. 本体 API​
3.1 本体 WebSocket 接口​
1. 必须先建立 control ，并取得 1201 返回的 session_id 与 bulkdata_bind_token 。​
2. 建立 bulkdata 后，首个数据帧必须发送 1202 绑定请求。​
3. 1202.data.session_id 和 1202.data.token 必须分别使用 1201 返回的会话 ID 和绑
   定令牌。​
4. 只有收到 1203 后， bulkdata 才视为绑定成功，可以继续传输业务数据。​
1. 客户端连接 ws://host:10010/control 。​
2. 网关主动返回 1201 kHandShakeAck ，客户端保存 client_id 、 session_id 和
   bulkdata_bind_token 。​

3. 如需重新获取会话信息，客户端可在 control 上发送 1200 kHandShake ，网关再次返回
   1201 。​

4. 客户端连接 ws://host:10010/bulkdata 。​
5. 连接建立后的第一条消息发送 1202 kBindBulkDataChannel 。​
6. 网关返回 1203 kBindBulkDataChannelAck ，确认绑定成功。​
7. 绑定成功后，客户端再发送或接收需要走 bulkdata 的业务消息。​

3.2 本体接口接入建议​
1. 连接阶段先完成 1201 握手和 1202/1203 通道绑定，再发送本体控制请求或接收状态推送。​
2. 控制类请求使用 1302 、 1304 、 1310 ；响应类消息以 1303 、 1311 的 status_code
   和 message 判断受理结果。​
3. 状态页以 1315 为主，故障页以 1317 为主，诊断工具接收 1319；地图页面分别处理
   1401/1403/1405/1407。​
4. 状态推送与算法任务 5009 分开存储和展示； 5009 表示算法任务状态， 1315 表示本体状
   态，不能相互覆盖。​
5. 断线重连后重新处理 1207 、 1521 、 1525 ，并用消息时间戳避免旧状态覆盖新状态。​
